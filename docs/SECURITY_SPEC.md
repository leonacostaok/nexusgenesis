# NexusGenesis 安全规范(v0)

## 1. 目标安全模型(未来主网理想状态)

### 1.1 密钥与身份
- **签名算法**: using Dilithium2 作为标准签名算法
- **密钥规格**:
  - 公钥长度: 2,592 字节
  - 私钥长度: 4,864 字节
  - 签名长度: 4,595 字节
- **身份管理**:
  - 用户地址: 基于公钥哈希的 Base58 编码格式
  - 节点身份: 独立的身份体系, 与钱包分离
  - Observer: 拥有明确的链上身份和权限
- **密钥存储**: 私钥应在 HSM 或安全模块中持有, 不在明文文件中长期存在

### 1.2 交易与签名
- **签名要求**: 所有链上关键交易(TRANSFER / GOVERNANCE_* / AGENT_REGISTER / OBSERVER_EVENT 等)都必须由相应私钥签名
- **验签执行**: 交易验签必须严格执行, verification failed一律拒绝
- **sign message体**: 包含交易核心字段的规范化 JSON 序列化

### 1.3 通信安全
- **P2P 加密**: 节点间 P2P 通信需要via Kyber 等 PQC 手段进行密钥协商与加密
- **敏感数据**: 禁止明文传输敏感数据
- **TLS 层**: 生产环境应using TLS 加密

### 1.4 节点安全
- **DoS 防护**: 节点应有基础的 DoS 防护, 速率限制
- **日志安全**: 日志中不应记录私钥, 完整签名原文等敏感信息
- **访问控制**: 内部 API 接口应有严格的访问控制

### 1.5 治理与 Observer
- **Observer 身份**: Observer 拥有明确的链上身份
- **权限模型**: Kill Switch / APPROVE_SPEND / REJECT_SPEND 等操作都要可审计, 有明确权限模型
- **审计追踪**: 所有治理操作应有完整的审计日志

## 2. 当前 DevNet 安全现状

### 2.1 密钥与身份
- **实现方式**: using superdilithium 库实现 Dilithium2
- **密钥存储**: 公钥和私钥存储在 JSON 文件中, 明文存储(未加密)
- **身份体系**: 节点身份与钱包复用, using相同的地址
- **地址格式**: ng1 + Base58(1 字节版本 + 20 字节公钥哈希 + 4 字节校验和)

### 2.2 交易与签名
- **签名验证**: DevNet 正常运行时默认启用 STRICT_SIGNATURE_VERIFY = true, 支持真实的 Dilithium2 验证
- **test环境**: 为了方便test, 有一个禁用严格验证的开关, 仅用于单元test场景
- **交易类型**: 支持 TRANSFER, GOVERNANCE_PROPOSAL, GOVERNANCE_VOTE, OBSERVER_EVENT, AGENT_REGISTER(DevNet 已实测via)
- **签名字段**: 所有交易类型都有签名字段
- **test覆盖**: security.test.js 中有针对签名的test
- **密钥存储**: completed加密钱包的生成, 保存, 导出和加载test, 支持 AES-256-CBC 加密存储
- **Observer 身份验证**: 已验证未注册地址无法发送 OBSERVER_EVENT 交易, 系统正确返回错误信息
- **实现库**: using superdilithium 2.0.6 库实现
- **参数集**: 当前using superdilithium 默认参数集, 公钥长度约 2,592 字节, 签名长度约 4,595 字节, 安全强度不低于 Dilithium2

### 2.3 通信安全
- **P2P 通信**: using WebSocket 明文通信, 无加密
- **Kyber 集成**: 未集成任何 Kyber 或 TLS 层
- **HTTP 接口**: 仅绑定 127.0.0.1, 无额外认证

### 2.4 节点安全
- **速率限制**: 无明确的速率限制或 DoS 防护
- **日志安全**: 日志中可能会出现敏感字段(如完整地址, 公钥, 签名)
- **访问控制**: HTTP 注入接口无认证机制

### 2.5 治理与 Observer
- **Observer 实现**: 任意地址可发送 OBSERVER_EVENT, 无身份验证
- **权限控制**: 无权限控制机制, 任何地址都可以触发高危操作
- **审计机制**: 有基本的日志记录, 但无完整的审计追踪

## 5. test环境设置

### 5.1 签名验证开关
- **config item**: `STRICT_SIGNATURE_VERIFY`
- **默认值**: `true` (DevNet 和主网)
- **testmode**: 可设置为 `false` 以跳过签名验证, 仅用于单元test场景
- **目的**: 为了让test用例跑得更快, 不受 PQC 实现性能影响

### 5.2 superdilithium 参数说明
- **库版本**: superdilithium 2.0.6
- **参数集**: using默认参数集
- **密钥长度**:
  - 公钥: 约 2,592 字节 (Hex 编码后约 5,184 字符)
  - 签名: 约 4,595 字节 (Base64 编码后约 6,127 字符)
- **安全级别**: 安全强度不低于 Dilithium2
- **说明**: 当前using的参数集可能与 NIST 标准 Dilithium2 的典型参数(pk ≈ 1312 字节, sig ≈ 2420 字节)不同, 这是由于 superdilithium 库的实现特性, 安全强度不低于标准 Dilithium2

## 6. 最高优先级安全债

根据风险与实现代价综合判断, 最高优先级的 3 条安全债是: 

1. **交易签名验证** (风险: 中) - 确保所有关键交易类型都经过真实的 Dilithium2 验证
2. **密钥存储** (风险: 高) - 实现私钥加密存储, 防止私钥泄露
3. **Observer 身份验证** (风险: 中) - 实现 Observer 注册与权限模型, 防止恶意操作

## 8. 安全债优先级声明

在更多 AI / 更多真实用户加入前, 安全债清单中的前三条必须至少达到 v1 水平: 
1. **交易签名验证** - 确保所有关键交易类型都经过真实的 Dilithium2 验证
2. **密钥存储** - 实现私钥加密存储, 防止私钥泄露
3. **Observer 身份验证** - 实现 Observer 注册与权限模型, 防止恶意操作

其他安全债(Kyber/P2P 加密, HSM 集成, 攻击面test等)视后续资源与需求分阶段推进. 

## 9. 安全最佳实践

### 9.1 开发最佳实践
- **密码学库using**: 始终using最新版本的密码学库, 定期更新依赖项以修复安全漏洞
- **代码审计**: 定期进行代码security audit, 特别关注密码学实现和签名验证逻辑
- **test覆盖**: 确保所有安全相关功能都有充分的test覆盖, 包括边界情况
- **安全日志**: 实现结构化的安全日志, 记录关键操作和异常情况
- **最小权限**: 遵循最小权限原则, 只授予必要的权限

### 9.2 部署最佳实践
- **密钥管理**: using硬件安全模块(HSM)存储私钥, 避免明文存储
- **网络安全**: 配置防火墙, 限制网络访问, 只开放必要的端口
- **监控告警**: 实现安全监控和告警机制, 及时发现异常行为
- **定期备份**: 定期备份钱包和区块链数据, 防止数据丢失
- **环境隔离**: 生产环境与开发环境隔离, 避免敏感信息泄露

### 9.3 操作最佳实践
- **密钥备份**: 实施多重签名和密钥备份机制, 防止密钥丢失
- **安全更新**: 及时应用安全补丁和更新, 保持系统安全
- **访问控制**: 实施严格的访问控制, 限制对敏感资源的访问
- **安全培训**: 为开发和运维人员提供安全培训, 提高安全意识
- **应急响应**: 制定安全事件应急响应计划, 定期进行演练

### 9.4 安全test指南
- **单元test**: 编写针对密码学操作和签名验证的单元test
- **集成test**: test不同模块之间的安全交互
- **渗透test**: 定期进行渗透test, 发现潜在的安全漏洞
- **模糊test**: 对输入数据进行模糊test, 发现边界情况
- **性能test**: test安全操作的性能, 确保不会成为性能瓶颈
