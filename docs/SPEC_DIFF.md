# SPEC_DIFF: 白皮书 vs 实现 v0.1 差异说明

## 1. 地址规范差异
- 白皮书: 公钥 → SHA3-512 → 前 40 字节 → 校验和 + `ng` 前缀 → Base58
- 实现 v0.1: `ng1` + 20 字节 + 4 字节, 具体见 PROTOCOL_UNIFICATION.md

### 1.1 差异原因
- **实现复杂度**: using 20 字节 payload 简化了实现, 减少了计算复杂度
- **依赖库限制**: 当前using的 superdilithium 库和哈希库在某些环境下对 40 字节处理支持有限
- **性能考虑**: 20 字节 payload 减少了地址长度, 提高了传输和存储效率
- **跨语言兼容性**: 20 字节方案在 JavaScript 和 Python 之间更容易保持一致

### 1.2 未来迁移计划
- **迁移计划**: 计划在 v1.0 版本迁移到白皮书版地址格式
- **版本标签**: 
  - v0.x: 当前实现(20 字节 payload)
  - v1.0: 完全符合白皮书规范(40 字节 payload)
- **向后兼容策略**: 
  - v1.0 节点将继续接受 v0.x 地址格式的交易
  - 提供地址转换工具, 允许用户将 v0.x 地址转换为 v1.0 格式
  - 新生成的地址将using v1.0 格式

## 2. 其他差异

### 2.1 AINVM 状态
- **白皮书**: 设想了完整的 AINVM(AI Native Virtual Machine)
- **实现 v0.1**: 未实现 AINVM, 仅实现了基础的 P2P 通信和钱包功能
- **计划**: 在 Epoch 1 阶段开始实现 AINVM 原型

### 2.2 Kyber 加密
- **白皮书**: 设想using Kyber 进行加密通信
- **实现 v0.1**: 仅实现了 Dilithium2 用于签名验证, 未实现 Kyber 加密
- **计划**: 在 P2P 通信稳定后, 集成 Kyber 加密以增强通信安全性

### 2.3 经济模型
- **白皮书**: 提出了完整的经济模型和 NGEN 分配机制
- **实现 v0.1**: 未实现完整的经济模型, 仅实现了基础的钱包功能
- **计划**: 在当前阶段complete经济模型草案, 为 Epoch 1 做准备
